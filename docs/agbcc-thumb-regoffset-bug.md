## Thumb backend never emits register-offset addressing (`ldr Rd, [Rb, Ro]`)

### Summary

The Thumb compilers (`agbcc` and `old_agbcc`) never generate Thumb's
register-offset load/store addressing mode. They always materialise the address
into a register first and then use an immediate-offset access. `agbcc_arm`, built
from the same tree, generates the equivalent ARM addressing mode without
difficulty — so this looks like a gap in the Thumb machine description rather
than a deliberate choice.

This matters for matching decompilations: real AGB ROMs use the mode heavily, and
any function containing it currently cannot be matched.

### Environment

- agbcc built from pret/agbcc, installed via `./install.sh`
- Version banner: `@ Generated by gcc 2.9-arm-000512 for Thumb/elf`
- Host: macOS (arm64), binutils `arm-none-eabi`
- Affects **both** `agbcc` and `old_agbcc`

One environment detail worth stating up front, in case it prompts a "did your
build go wrong?" question: **the build host has a case-insensitive filesystem**
(macOS/APFS default — `touch AAA; touch aaa` leaves one file). That is a real
hazard for old GCC source trees generally, so it is fair to ask. I do not think
it is the cause here; see "Not a corrupted build" below.

### Reproducer

One line of C, no headers, no include path:

```c
unsigned char f(unsigned char *p, int i) { return p[i]; }
```

```sh
printf 'unsigned char f(unsigned char *p, int i) { return p[i]; }\n' > repro.c

tools/agbcc/bin/agbcc     -O -o - < repro.c   # Thumb
tools/agbcc/bin/old_agbcc -O -o - < repro.c   # Thumb, older variant
tools/agbcc/bin/agbcc_arm -O -o - < repro.c   # ARM, for comparison
```

### Actual vs expected

Both Thumb compilers produce:

```
f:
        add     r0, r0, r1
        ldrb    r0, [r0]
        bx      lr
```

Expected (and what the ARM compiler from the same tree does produce):

```
        ldrb    r0, [r0, r1]        @ agbcc_arm output, ARM encoding
```

Thumb has the same capability — `LDRB Rd, [Rb, Ro]`, encoding format 7 — so the
Thumb output should be a single instruction as well.

This is the most favourable possible case: base and index both arrive in argument
registers, there is nothing to schedule, and no addressing legalisation should be
required. It still misses.

### Scope

Not specific to `unsigned char` or to that expression form. I tried six shapes and
none produced the mode:

```c
unsigned char  g1(unsigned char *p, int i)          { return *(p + i); }
unsigned char  g2(unsigned char *p, unsigned i)     { return p[i]; }
unsigned short g3(unsigned short *p, int i)         { return p[i]; }
unsigned char  g4(volatile unsigned char *p, int i) { return p[i]; }
int            g5(unsigned char *p, int i, int n)   { int s=0; while(n--) s += p[i++]; return s; }
unsigned char  g6(unsigned char *p, int i)          { return *(unsigned char *)((int)p + i); }
```

Zero register-offset instructions across:

| compiler | `-O` | `-O2` |
|---|---|---|
| `agbcc` | 0 | 0 |
| `old_agbcc` | 0 | 0 |

Stores behave the same way (`p[i] = v` → `add` then `strb Rd, [Rb]`).

### Why this matters — evidence from a real ROM

I am working on a matching decompilation of Golden Sun (GBA, 2001), which the
evidence says was built with this compiler: with the right flags agbcc reproduces
whole functions byte-for-byte, including the `pop {rN}; bx rN` interworking
epilogue.

In the disassembled ROM:

- **818 of 2259 functions (36.2%)** contain at least one register-offset
  load or store
- **4369 such instructions** in the ROM proper, plus 2514 more in the overlays

All eight forms appear, so this is not one missing pattern but the whole family:

| form | count | form | count |
|---|---|---|---|
| `ldrsh` | 1527 | `ldrsb` | 398 |
| `ldrb` | 643 | `str` | 227 |
| `ldr` | 625 | `strh` | 182 |
| `ldrh` | 618 | `strb` | 149 |

A representative function — ordinary array indexing, nothing exotic:

```
Func_793b8:                     /* return ewram_40[(idx & 0xFFF) >> 3]; */
        lsl     r3, r0, #20
        lsr     r0, r3, #23
        ldr     r3, =ewram_40
        ldrb    r0, [r3, r0]    <-- agbcc emits: add r0, r3, r0 / ldrb r0, [r0]
        bx      lr
```

That function is five instructions long and misses by exactly one. Register pins
(`register T x asm("r3")`) fix the register allocation but cannot produce the
addressing mode.

### This is compiled code, not hand-written assembly

Worth ruling out, since a uniform idiom could suggest hand-written asm. It does
not hold up: **781 of the 813 affected functions — 96.1% — also carry agbcc's
`-mthumb-interwork` epilogue** (`pop {rN}; bx rN`), which only appears when that
flag is on. Hand-written assembly has no reason to adopt the compiler's
interworking convention 781 times.

So the original toolchain emitted these instructions from C, and the
reconstruction does not.

### Not a corrupted build

Given the case-insensitive host above, the obvious alternative explanation is
that something went wrong when agbcc was built rather than being absent from the
sources. Three things argue against it:

1. **`agbcc_arm` works.** It is built from the same tree, in the same build, and
   installed alongside the others — and it emits the ARM equivalent correctly
   from the same one-line reproducer. A build problem would have to damage the
   Thumb path while leaving ARM intact.
2. **The Thumb compilers are otherwise byte-exact.** They reproduce whole
   functions from this ROM instruction for instruction, including the
   interworking epilogue and the original's specific register allocation. A
   mis-built compiler does not land on that; it produces wrong code or fails to
   build.
3. **`config/arm/` has no case-colliding filenames** — `arm.md` / `arm.c` /
   `arm.h`, `thumb.md` / `thumb.c` / `thumb.h`, all lowercase. (The binary does
   reference `thumb.c`, which confirms that is the backend file in play.)

If a maintainer nonetheless suspects the build, I am glad to rebuild inside a
case-sensitive disk image and re-test — it is a cheap check.

### Where the fix probably lives

**Flagging clearly: I have not read agbcc's sources** — my install is binaries
only (`bin`, `include`, `lib`), so the following is inference from how GCC 2.x ARM
backends are usually organised. Maintainers will know the tree far better.

In a GCC 2.x ARM/Thumb backend I would expect three things to need to agree:

1. **Address legitimation** — `GO_IF_LEGITIMATE_ADDRESS` (Thumb arm) must accept
   `PLUS (reg, reg)` for the relevant modes. If it rejects that form, everything
   downstream is moot because `LEGITIMIZE_ADDRESS` will force the `add`.
2. **Patterns/constraints** — the `movqi`/`movhi`/`movsi` and the
   `zero_extendqisi2` / `extendqisi2` / `extendhisi2` patterns in the Thumb `.md`
   need an alternative whose memory operand accepts that address.
3. **Operand printing** — the address printer must emit `[rb, ro]` for that form.

One nuance specific to Thumb that may explain the omission: the register-offset
encoding only reaches **r0–r7**, and there is no immediate-offset variant that
mixes with it, so the constraint letter has to be low-register-only. If the
original implementation attempt hit that and was dropped, that would fit the
symptom exactly.

Given `agbcc_arm` handles the ARM equivalent from the same tree, a diff of the
ARM and Thumb address-legitimation paths seems like the obvious starting point.

### What I did not verify

- I have not read agbcc's source, so I cannot point at a specific file or line.
- I have not confirmed whether upstream GCC 2.9 ever supported this for Thumb.
  If it did not, then the original SDK compiler carried a Nintendo modification
  that this reconstruction does not, which is a different (and larger) finding —
  but the practical effect is the same.
- I have not tested `-Os` or flag combinations beyond `-O`/`-O2` with and without
  `-fcall-used-r4`/`-fcall-used-r5` and `-mthumb-interwork`.

### Impact if fixed

For this project it would unlock roughly a third of the ROM for matching in a
single change. I would expect a similar effect for any other matching decomp
targeting an AGB title built with this toolchain.

I am happy to test a patch against a real ROM — I have 2259 annotated functions
and a byte-exact build to check against, so I can give a precise before/after
count of how many functions become reachable.
