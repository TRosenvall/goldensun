## The parked function was the best target in the queue

`OvlFunc_906_2008314` had been parked with a note recording two residual
diffs. It turned out to head the **largest family in the overlays** — 18
functions, one `GetEntrances` per map, each choosing between two
edge-transition tables on a `gState` halfword.

Both diffs are now fixed, and each needed a technique that already existed
elsewhere in the tree:

**1. Runtime address arithmetic.** The ROM loads `&gState` with a zero addend
and builds `0x1c0` at runtime:

    ldr r3, =gState / mov r1, #0xe0 / lsl r1, #1 / add r3, r1

Every plain pointer or integer spelling folds `0x1c0` into the pool addend
instead. Writing the arithmetic out as separate statements over a typed
`GlobalState` reproduces it — the same shape already matching in
`src/overlays/rom_7b7790/ovl_314_c_c_a_b.c`.

**2. The pooled compare.** `ldr r3, =0x1d / cmp r2, r3` where `cmp #0x1d`
would fit is the pool tell, fixed with `_ID_1d` as in batch 07.

The parked note had **diagnosed both correctly**. For the first it proposed
"the real struct type (GS-headers) or the permuter". It needed neither — only
an in-tree precedent that happened to be written three batches later.

**The lesson is about the park, not the function.** A parked function is not a
graveyard entry; it is a queue item that gets cheaper every time a technique
lands. Re-screening the park after each breakthrough should be routine, not
something done when the candidate list runs dry. Doing it here turned one
parked function into ten.

## Two mistakes worth recording

Both were mine, and both were caught by tooling rather than review:

- A file header containing `char*/int` — the `*/` closed the comment block and
  the translation unit would not parse. Caught by `tools/tryc.py` before it
  reached the build.
- `""` left in a `startswith()` prefix tuple in `tools/name_evidence.py`.
  `"".startswith("")` is true for *every* string, so the filter silently
  discarded every input rather than failing. It reported 57 functions with no
  evidence attached, which looked like missing data rather than a bug.

## Naming evidence is now being captured

Per your plan to name functions before handing over, `docs/names.md` is
generated by `tools/name_evidence.py` and records, for every function we
elevated, a proposed name **and the basis for it**:

| Basis | Meaning | Safe to rename unchecked? |
|---|---|---|
| `read` | we described it ourselves while elevating | yes |
| `named` | the annotation proposes an identifier | yes — checkable in seconds |
| `call-trace` | the annotation is explicitly a call list, not a description | no |
| `annotation` | inherited prose asserting purpose | **no — verify** |

This matters because `docs/attribution.md` records that the inherited corpus
gets mechanism right and **purpose wrong** often enough to matter. Recording
only the name would launder a guess into a fact.

Current state: **2 `named`, 63 `read`**, and no rows at the weaker bases.
