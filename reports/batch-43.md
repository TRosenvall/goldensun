*Status: ready to port.*

For porting into `Coaltergeist/goldensun-decomp`. Assumes batches 01–42 are in.

Verified against `baserom.gba` (SHA1 `5c4695205413df7db52b9a184815a07783999971`)
from a clean `make clean && make -j8 && make compare` — 96 overlays compared
byte-for-byte and `goldensun.gba: OK`. Every address read back from the linked
ELF with `nm`, both new symbols from `stage1.o`.

## Read this first: `--orphans` passed a tree that did not link

`asm/overlays/rom_78dc80/ovl_30_c_c.s` held **one function and a `.data` section
of four `.incbin` blobs**. The function count was checked, the whole file
converted, the `.s` deleted — and `tools/asmfacts.py --orphans` reported **zero
orphans**, because the `.o` did still have a source, just not one that produces
the section the linker script asks for. The link failed with three undefined
references.

`tools/split_s.py` refuses that shape and would have said so. It was never run,
because the file looked like a one-function file.

**The first fix was also wrong**, and that is worth as much as the fix.
Flagging every linker entry that wants `.data` from a `.c`-built object reports
**twenty** pre-existing cases in your tree, all harmless — `ld` contributes
nothing and the build is green. A check that fires twenty times on a correct
tree is worse than no check at all.

What shipped asks a narrower, answerable question: **which `.s` files has this
working tree deleted, and does a linker script still want `.data` or `.bss` from
them?** Zero false positives on a clean tree, fires on the exact broken state.
Both versions are in the docstring.

It also had to learn what every other tool here has learned: the build writes
gcc's output to `asm/<path>.s`, so an elevated function leaves a file that
**looks** like an assembly source and is not one. It reads the
`@ Generated by gcc` marker.

## Three acceleration ideas, all measured, all dropped

This closes a line of work that ran from batch 32.

| idea | measured | verdict |
|---|---|---|
| mechanical C generator for straight-line call scripts | 110 functions, 1% of instructions | no |
| fragment matcher (blocks vs whole functions) | 6 functions, 0.5% | no — the first ranking said 25% and was counting fakematches |
| generator relaxed to allow control flow | 183 functions, 2% | no |

All three are small for the same reason: **that population has already been
consumed by hand.** The tooling that mattered — the shape matcher, the park
ranker, the flag sweep, the compiler source — is built and its leverage is
spent. What remains is reading a ROM listing and writing C, per function, and
the only lever left is fewer round-trips: batch the screening, batch the build,
and stop writing long headers for functions that only reuse known levers.

Most of the files in this batch have three-line headers for that reason.

## The catalogue saved a round

`OvlFunc_946_2009494` was **skipped without screening**. It is straight-line and
carries two two-instruction constants split around other arguments, and batch
42's reading of `local-alloc.c` says that is unreachable in plain C. Thirty
seconds of reading replaced a screen and an iteration — the first time the
settled theory prevented work rather than explaining a failure afterwards.

**`Func_8096af0` is worth a look.** The ROM does `ldrsh` and then compares with
`bhi` — the value is read as a **signed** halfword and widened to **unsigned**
before the switch. A plain `short v` gives `bgt` and is one instruction out.
The load and the compare disagree, which one variable declaration cannot
express and a cast has to.

## Parked

`OvlFunc_893_2008054`, `OvlFunc_894_2008054` (byte-identical twins in adjacent
overlays) and `OvlFunc_973_200871c`, all 3 of 30, one shared cause:

    rom    add r2, r1, r3 / mov r3, #0x10 / str r3, [r2]
    ours   mov r2, #0x10 / str r2, [r1, r3]

**The first store in each function is correct.** For it, the offset is modified
between the address computation and the store, so gcc must materialise the
address; for the second the offset is dead once the address is formed, so gcc
folds it into a register-offset store. The ROM materialises both and reuses the
offset register as the stored value.

The construct that should fix it is the worst result — reassigning the offset as
the value gives **10 of 30**, because it changes the register allocation eight
instructions earlier and base and offset swap. Six formulations and five flags
recorded.

Also parked: the pre-header-load-merge family is now diagnosed rather than
merely observed. At `-O1` all three members go to 2 and land on the **same** two
instructions — a two-instruction loop limit whose `mov`/`lsl` pair the ROM
splits around the counter increment. That is arg-interleave inside a loop body,
which `local-alloc.c` says is unreachable: `REG_N_REFS` is weighted by
`loop_depth`, so a set-once-used-once pseudo counts 4 there, not 2. Three parks,
one blocker, and a closed one.
