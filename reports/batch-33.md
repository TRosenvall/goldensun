## `tools/match_shapes.py`

Batch 32 ended by flagging the cheapest available improvement to the tooling.
This is it, and its first run produced this entire batch — **five functions, all
five matching on the first screen.**

The tree already had three rankers, and all three ask a version of *what looks
easy*:

| tool | question |
|---|---|
| `elevation_candidates.py` | what is small, few calls, few branches |
| `pick_candidates.py` | what is unlikely to hit a blocker we know about |
| `find_twins.py` | what appears more than once in the REMAINING assembly |
| **`match_shapes.py`** | **what looks like something already written** |

The fourth question is stronger, because a shape that has matched once comes
with a finished `.c` to copy. Batch 32 found five functions that way by hand —
noticing a shape had siblings and grepping for them — and four matched
immediately. That was worth automating.

**It works because the solved corpus is already in the tree in assembly form.**
The build writes gcc's output to `asm/<path>.s`, beside and over the
hand-written original (the `asm/%.o: src/%.c` rule). Those files announce
themselves with `@ Generated by gcc`, so 2,439 solved functions can be compared
directly against the 2,994 unsolved ones, in the one representation both have.

Bodies reduce to a **skeleton**: mnemonic plus operand *kinds*, with registers,
immediates, memory operands and symbols each collapsed to a letter. Two
functions with the same skeleton differ only in constants, registers and callee
names — which is exactly the relationship that makes "copy the `.c` and change
the numbers" work.

### The destructive-form collapse is load-bearing

The first version reported **4 leads**. The fixed version reports **20**, on the
same tree. The difference is one fold:

    gcc emits           lsl r2, r2, #2
    the ROM disassembly lsl r2, #2

Without treating those as the same instruction the two corpora share almost no
shapes at all. `tryc.py` has normalised exactly this since its first version —
it is the first row of the "What the screen has to normalise" table in
`docs/elevation.md` — and it still had to be rediscovered here, because **a
skeleton looks nothing like an instruction diff** and nothing carried the
knowledge across.

Worth remembering for the next tool that compares the two corpora: the three
spellings in that table are not screen-specific, they are properties of the two
representations.

### What it is not

A shape match is a lead, not a proof. Callee names are collapsed, which is the
loosest part, and the report prints the exemplar's path so the `.c` gets read
before it is copied. `tools/find_families.py` records what a genuinely loose
match cost — nine false positives, 450-to-1500-instruction functions grouped
because they shared a few call names, and two splits that had to be reverted —
so this stops well short: instruction count, mnemonic sequence, and every
operand's kind must agree exactly. Parked functions are skipped.

Fifteen leads remain after this batch.

### One correction to what that family knows

The exemplar's note reads as though the shared value — one that appears both as
a register argument and as a stack argument — must always be named once and used
twice. **It does not.**

In `OvlFunc_956_200824c` the second argument and the `[sp,#4]` value are the
same `0x3d`, and writing it as a shared local and as a literal produce
**identical output**. A value small enough for an eight-bit `mov` is
rematerialised either way. The sharing only becomes visible, and only then needs
naming, when the value is expensive enough that gcc would rather keep it than
rebuild it.

Same reading applies to `OvlFunc_898_2008ecc`, where `0x17` is both leading
arguments *and* the `[sp]` value: only the stack one is named, because the ROM
materialises the other two fresh with their own `mov`s. Naming them would
produce register copies that are not in the ROM. That is the batch-31 rule from
`OvlFunc_935_2008410`, seen again.
